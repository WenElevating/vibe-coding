Mobile 模块整理 / 分层讨论

当前目标：降低 UI 修改连锁反应、理清业务数据流、提高可测试性，并支撑后续大功能开发。

1. 当前模块地图

AppappLanAiCliControlApp：只负责 MaterialApp 组合，已经很薄。
ShellshellMobileShell、RoutePage、AppSnapshot：顶层导航、全量 snapshot 加载、页面装配。现在是主要协调层。
features/workbench编码主工作台、composer、事件卡、消息转换、workspace transition。当前最大热点。
features/sessions会话列表、SessionItem、session merge / view model。
features/workspace_picker工作区列表、创建/打开工作区、display helper。
features/settings设置页面、shell route 回调、全局偏好项。
features/run_detail运行详情页面。
leaf featuresadapters / diagnostics / notifications：相对薄的展示页面。
modelsdaemon protocol DTO。
servicesDaemonClient / ConversationClient。
stateconversation reducer、dashboard/run detail state。
widgets + theme共享 UI primitives 和 design tokens。
Testingtestingdebug helpers + preview builders，目前通过 package barrel 暴露给 widget tests。

2. 三种分层路线

方案 A

共享内核 + 业务层

把 theme/widgets/models/services/state 作为 shared/core，features 只放页面与本地状态，shell 负责导航。

优点

  • 边界直观
  • 迁移成本较低
  • 适合继续稳态整理

代价

  • feature 内部仍可能膨胀
  • workbench 热点不会自然消失
方案 B · 推荐

垂直切片 + 轻壳层

每个 feature 拥有自己的 page / controller / view_model / barrel；shell 只做路由和壳装配，shared 层只保留真正通用的 primitives。

优点

  • 最贴近“改一个模块只动一个模块”
  • 适合继续拆 workbench/sessions/workspace
  • 新增功能边界自然

代价

  • 需要继续清理页面级状态
  • shared 层必须更克制
方案 C

严格分层架构

app → shell → feature controllers → feature views → shared primitives，状态和逻辑通过 controller/VM 全面下沉。

优点

  • 数据流最清晰
  • 可测试性最强
  • 长期规范性好

代价

  • 改动面最大
  • 抽象层和文件数明显增加
  • 当前阶段可能过重

推荐路线

建议选 方案 B：垂直切片 + 轻壳层。它能同时满足 A/B/C/D 四个目标，而且不会把刚完成的 import 边界迁移推翻。后续重点不是再造大框架，而是把热点模块按 feature 内部边界继续切薄。

4. 第一阶段建议

Workbench继续拆：conversation controller、workspace/session selection state、message/event mapping。
Shell瘦身：AppSnapshot 不再无限扩张，后续逐步改成 feature-scoped loading。
Testingpreview builders 按 feature 归属，testing barrel 只聚合，不承载业务。
