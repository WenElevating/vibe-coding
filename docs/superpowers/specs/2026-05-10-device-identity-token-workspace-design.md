# Device Identity, Short-Lived Token, and Workspace Binding Design

Date: 2026-05-10
Status: Draft for review
Scope: Mobile device identity persistence, daemon device records, short-lived access tokens, and workspace ownership binding

## 1. Problem

The current mobile/daemon handshake treats device identity as a temporary pairing result. That makes the device identity unstable across app restarts, which in turn makes workspace ownership appear to disappear after reconnect. The symptom is not that workspace persistence is missing; the deeper issue is that the identity used to bind workspaces is not stable.

The product requirement is to make device identity durable while keeping access credentials short-lived. The mobile client should generate one device identifier per installation, persist it locally, and reuse it for future pairings or logins. The daemon should store the device identity in a dedicated device table, then bind newly created workspaces to that device so the same device can recover the same workspace set after restart.

## 2. Goals

- Keep one stable `deviceId` per device installation.
- Have the mobile client generate and persist `deviceId` locally.
- Keep access credentials as short-lived `token`s that can expire and refresh.
- Store device records on the daemon in a dedicated table.
- Bind each workspace to the owning device record at creation time.
- Make workspace listing and workspace-scoped actions resolve through device ownership.
- Preserve the existing authorization model: `token` authenticates the request, `deviceId` identifies ownership, and workspaces attach to device ownership.

## 3. Non-Goals

- Do not introduce username/password account management.
- Do not make `deviceId` itself a secret or a long-term bearer credential.
- Do not replace token-based request authentication with device-id-only authorization.
- Do not redesign the workbench routing architecture in this change.
- Do not rewrite existing conversation/session persistence unless it is required to bind workspace ownership.

## 4. Terminology

- `deviceId`: A stable identifier generated by the mobile client once per installation and reused across launches.
- `token`: A short-lived access credential issued by the daemon after pairing or login. It can be refreshed and revoked.
- `device record`: The daemon-side persisted representation of a device identity.
- `workspace ownership`: The relationship between a workspace and the owning device record.

## 5. Architecture

Use a three-layer split:

```text
Mobile client
  DeviceIdentityStore
  DaemonClient.ensurePaired(...)

Daemon authentication layer
  devices table
  token issuance / refresh / revocation

Daemon workspace layer
  workspaces table with device ownership
  workspace queries filtered by device
```

### 5.1 Mobile responsibilities

- Generate a RFC 4122 UUID v4 `deviceId` on first launch.
- Persist `deviceId` locally with the app's storage mechanism. The identifier format must be a lowercase canonical UUID v4 string with hyphens.
- Read the same `deviceId` on every restart.
- Send the `deviceId` when pairing or logging in.
- Store the access token and refresh token separately from the device identity.
- Store the access token in ordinary app storage if needed for quick reuse, but store the refresh token in secure storage (iOS Keychain / Android Keystore-backed secure storage on native platforms).

### 5.2 Daemon responsibilities

- Accept the client-supplied `deviceId` during pairing or login.
- Store the device identity in a dedicated table.
- Store the device identity as a BLAKE2b-based keyed HMAC (server-side pepper) for matching and audit.
- Issue short-lived tokens for authenticated requests.
- Bind new workspaces to the owning device record.
- Filter workspace lists and workspace-scoped actions by the owning device record.

## 6. Data Model

### 6.1 `devices`

Recommended columns:

- `id`: internal primary key used by foreign keys.
- `device_id_hash`: BLAKE2b keyed HMAC of the client `deviceId` using a server-managed pepper.
- `label`: user-facing device label.
- `status`: active, revoked, or disabled.
- `created_at`: creation timestamp.
- `last_seen_at`: last successful authenticated request timestamp.

Recommended indexes:

- Unique index on `device_id_hash`.
- Index on `status` for admin lookup and cleanup.
- Index on `last_seen_at` for activity-based maintenance.

Why hash instead of plain text:

- The client-supplied `deviceId` is stable but not secret.
- Storing it as a keyed BLAKE2b HMAC reduces exposure if the database is inspected.
- The daemon can still look up the device by hashing the incoming `deviceId` with the active pepper.

Pepper management:

- The daemon loads a server-side `device_id_pepper` from configuration or secret storage at startup.
- The active pepper is used for all new device writes.
- When rotating the pepper, the daemon keeps the previous pepper available for lookup until a background rehash migration completes.
- Device records are rehashed in place during the migration window so the previous pepper can be retired safely.

### 6.2 `device_tokens`

Recommended indexes:

- Unique index on `token_hash`.
- Index on `device_id`.
- Index on `token_type`.
- Index on `expires_at`.
- Index on `revoked_at` for cleanup queries.

Recommended columns:

- `id`: internal primary key.
- `device_id`: foreign key to `devices.id`.
- `token_type`: `access` or `refresh`.
- `token_hash`: hash of the issued token.
- `expires_at`: token expiry time.
- `revoked_at`: revocation time, if any.
- `created_at`: issuance timestamp.

Token TTL defaults:

- Access token default TTL: 15 minutes.
- Refresh token default TTL: 30 days.
- Both TTLs are configurable, but the access token should remain short-lived and the refresh token should remain materially longer-lived.

### 6.3 `workspaces`

Recommended columns:

- `id`: workspace identifier.
- `device_id`: foreign key to `devices.id`.
- `name`: workspace name.
- `path`: workspace path.
- `created_at`: creation timestamp.
- `updated_at`: update timestamp.
- `status`: active or archived.
- `archived_at`: archive timestamp, if archived.

The important part is that workspace ownership is tied to the device record, not to the short-lived token. Device revocation does not delete workspace rows; it only blocks access through the revoked device. Workspace archiving is a separate lifecycle concern.

## 7. Request Flow

### 7.1 First launch

1. Mobile checks local storage for `deviceId`.
2. If missing, mobile generates a new `deviceId` and saves it.
3. Mobile starts pairing or login with that `deviceId`.

### 7.2 Pairing or login

1. Mobile sends `deviceId` plus the pair/login input required by the existing flow.
2. Daemon hashes the incoming `deviceId` with the active pepper and looks up the device table.
3. If the device does not exist, daemon creates a new device record.
4. Daemon issues an access token and a refresh token.
5. Daemon stores both token hashes with explicit `token_type` values.
6. Mobile stores the access token separately from the `deviceId` and stores the refresh token in secure storage.

### 7.3 Token refresh

1. Before the access token expires, mobile calls the refresh endpoint.
2. Mobile sends the refresh token and the same persisted `deviceId`.
3. Daemon validates the refresh token against the device record.
4. Daemon issues a new access token and rotates the refresh token.
5. Old refresh tokens are revoked after successful rotation.
6. If the refresh token is invalid or revoked, mobile falls back to the normal pairing/login flow without changing `deviceId`.

### 7.4 Authenticated requests

1. Mobile sends the token with every authenticated request.
2. Daemon validates the token and resolves the owning device record.
3. Daemon updates `last_seen_at` for the device record.
4. Workspace queries and workspace-scoped actions are filtered through that device record.

### 7.5 Workspace creation

1. Mobile requests workspace creation while authenticated with a valid token.
2. Daemon resolves the current device record from the token.
3. Daemon creates the workspace with `device_id` pointing to that device record.
4. Subsequent workspace list queries for the same device return that workspace.

### 7.6 Restart and reconnect

1. Mobile restarts and reads the same persisted `deviceId`.
2. Mobile reuses or refreshes the short-lived token.
3. Daemon resolves the same device record.
4. The same workspace set is returned because the workspace ownership never changed.

## 8. Token Semantics

The access token is a short-lived credential, not a permanent device identity.

- It is issued after pairing or login.
- It can expire.
- It can be refreshed using the refresh token.
- It can be revoked without deleting the device record.
- It should not be used as the ownership key for workspaces.

The refresh token is a separate credential used only to obtain a new access token. It is not sent on ordinary API requests.

Default TTLs:

- Access token: 15 minutes.
- Refresh token: 30 days.

Both values are configurable so deployment environments can shorten or extend them without changing the protocol shape.

If an access token expires, the correct recovery path is to refresh it for the same device identity. The device identity itself does not change.

## 9. Error Handling

- Missing local `deviceId`: generate a new one and treat the app as a new installation.
- Invalid or revoked access token: refresh or re-pair without changing `deviceId`.
- Unknown device on the daemon: create a new device record from the client `deviceId`.
- Workspace creation failure: do not create a workspace row and do not create a partial device-workspace binding.
- Workspace list mismatch after refresh: keep the device identity stable and retry workspace sync rather than inventing a new identity.

## 10. Security Notes

- `deviceId` is an identifier, not a password.
- `access token` is the secret used for request authorization. `refresh token` is used only for token renewal.
- Storing `deviceId` as a BLAKE2b keyed HMAC on the daemon is recommended.
- Storing access-token and refresh-token hashes is also recommended using keyed BLAKE2b.
- The daemon should never depend on plaintext `deviceId` for authorization decisions.

## 11. Testing Strategy

- Unit-test that the mobile device identity store returns the same `deviceId` across reloads.
- Unit-test that `ensurePaired()` reuses the same `deviceId` rather than generating a new one.
- Unit-test that the daemon accepts a client-supplied `deviceId` and reuses the same device record.
- Unit-test that concurrent pairing requests for the same `deviceId` remain idempotent under a unique constraint.
- Unit-test that a workspace created by one device is returned only for that device.
- Unit-test that token expiration or refresh does not change the device identity.
- Unit-test that refresh rotates the refresh token and revokes the previous one.
- Regression-test that app restart does not create a new workspace ownership bucket for the same installation.

## 12. Migration Plan

1. Add a persistent client-side `deviceId` store.
2. Extend pairing/login requests to carry `deviceId`.
3. Add daemon device storage and lookups by hashed device identity.
4. Add workspace ownership by daemon device record.
5. Keep token issuance short-lived and independent from ownership.
6. Add regression tests around restart, refresh, and workspace recovery.
7. For existing installs, treat the first post-upgrade launch as a migration boundary: if no persisted `deviceId` exists, generate one and pair as a fresh device. If older client-managed credentials exist, attempt refresh/re-pair against the same daemon before falling back to a new pairing flow. The upgrade path should not invent a second device identity for the same installation.

## 13. Open Questions Resolved

- `deviceId` is fixed per installation, not per login.
- `token` is short-lived and refreshable.
- Workspace ownership is bound to device identity, not to token lifetime.
- Authorization remains token-based; ownership remains device-based.
